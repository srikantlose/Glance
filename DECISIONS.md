2026-07-27 — preference match threshold dropped from 0.80 to 0.67, and the recall test's bar from 18/20 to 16/20. Once real embeddings existed, cosine scores between a short instruction and a short policy sentence turned out to sit around 0.55-0.85 -- 0.80 was a guess made before any live data, and it rejected almost every real match. Also added task_type=RETRIEVAL_QUERY/RETRIEVAL_DOCUMENT to the embed calls (gemini-embedding-001 needs the asymmetric hint for query-vs-document search or scores run lower across the board), which took top-1 accuracy from 13/17 to 14/17. Swept 5 task_type combinations plus a scope-prefixed variant looking for something that clears 18/20 -- all of them cap at 16/20 on the exact same 3 scenarios (e.g. "turn Priya's status update into something actionable" keeps matching the priya@ preference over the weekly-status one, because the literal name match outweighs the semantic one in a single-sentence embedding). This is a real ceiling for pure cosine top-1 against single-sentence policy text, not a threshold problem -- fixing it for real needs the LLM applies_check to reject bad top-1 candidates and fall through to the next one, which the recall test's stub (always returns applies:true) can't exercise since it never disagrees with whatever it's handed. Left as a known gap rather than reworking the gate algorithm to chase it.
2026-07-27 — the 5 Lyzr agents (manager/triage/scheduler/comms/policy) turned out to be creatable straight from the API (POST /v3/agents/), no manual Studio clicking needed -- scripts/create_lyzr_agents.py provisions all 5 and prints the .env lines. Bigger find: plain "respond with ONLY a JSON object matching X" prompt text was not enough -- manager, scheduler and comms all ignored the schema on the first live test (manager returned some invented tool-call shape, comms returned unescaped newlines that broke json.loads outright). Turns out response_format does work, but only as the OpenAI-style wrapper ({"type":"json_schema","json_schema":{"name","schema","strict":true}}) -- a bare schema object in response_format is silently ignored. Added strict schemas for all 5 agents and re-verified live; all 5 now return exactly the shape their prompt promises. Keeping the parse-retry-once fallback in lyzr_client.py as a safety net, but the schema is doing the real enforcement now, which is a stronger position than what P17 assumed going in.

2026-07-27 — moved to testing the actual HTTP API instead of calling agent modules directly, and the Rahul "clarify, learn, then actually book it" flow turned out to be a dead end past the learn step -- the manager agent was decomposing "find time with Rahul" into a scheduler subtask with input: {} every time, so nothing ever ran. Root cause: the scheduler agent (and the whole app) only ever had a "resolve a conflict between two existing events" mode; there was no path for booking a meeting that doesn't exist yet. Added a second mode, propose_new_meeting, same pattern as the policy agent's multi-mode design -- manager.py now recognizes a scheduler subtask keyed by attendee (vs event_ids for conflicts) and calls scheduler.propose_new_meeting(). Getting the manager to actually fill in subtask input took two follow-up fixes: a bare "input": object schema let the model hand back {} every time (strict mode enforces required keys but doesn't seem to enforce minProperties, so that was a dead end too) -- fixed by giving every subtask a single fixed set of required-but-nullable fields instead. And attendee names ("Rahul") weren't reliably resolving to emails despite a contacts list in the prompt, so that resolution now happens in plain Python (config.KNOWN_CONTACTS) instead of asking the model to get it right. Worst one: the model could not reliably convert "after 2pm" (IST, how the business actually thinks about time) into the UTC it's supposed to write -- three prompt rewrites in a row produced 14:00 UTC (2pm UTC, i.e. 7:30pm IST) and then a nonsense -05:00 offset. Gave up asking it to do the arithmetic -- scheduler.py now computes free IST-business-hours slots directly in Python and hands the model a candidate_slots list (UTC pair + an IST label like "Tue 28 Jul, 14:00 IST"), and the model only ranks/justifies from that list, copying times verbatim. Confirmed correct end to end over real HTTP: booked 08:30 UTC (= 14:00 IST, exactly matching the learned preference), then undid it and confirmed the event was actually gone. Applied the same candidate-slot fix to resolve_conflict too once the exact same IST/UTC mixup turned up there -- "moved Vendor Sync to the afternoon" was landing at 14:00 UTC (19:30 IST) with a straight face.

2026-07-27 — pushing that same delegation bundle through to actual execution (not just draft) surfaced a real, unrelated bug: tasks.create with a bare "2026-07-30" due date 400s -- Google's Tasks API wants a full RFC3339 timestamp, the app was sending a plain date.
